# File Structure

[src/mastra](Entry point for all Mastra-related code and configuration)
[src/mastra/public](Contents are copied into the .build/output directory during the build process, making them available for serving at runtime)
[src/mastra/agents](Define and configure your agents - their behavior, goals, and tools)
[src/mastra/workflows](Define multi-step workflows that orchestrate agents and tools together)
[src/mastra/tools](Create reusable tools that your agents can call)
[src/mastra/mcp](Implement custom MCP servers to share your tools with external agents)
[src/mastra/scorers](Define scorers for evaluating agent performance over time)

## Mastra-Owned Postgres Tables

The concrete Mastra storage class wired into this feature is **`PostgresStore`** (from `@mastra/pg`), built by `buildStore()` in `memory/memory.factory.ts` and used both for conversation memory (`buildMemory()`) and as the `Mastra` instance's `storage` (`index.ts`'s `buildMastra()`). It runs on the **same Postgres connection pool** (`PG_POOL`, `src/infrastructure/database/drizzle.constants.ts`) as the rest of the app, but scoped to a dedicated **`mastra`** schema — the `MASTRA_PG_SCHEMA` constant in `mastra.constants.ts`.

At boot, `@mastra/core`'s `Mastra` class calls `PostgresStore.init()` internally (on first storage access), which creates and owns these tables in the `mastra` schema:

- `mastra.mastra_threads` — conversation threads
- `mastra.mastra_messages` — per-thread message history
- `mastra.mastra_resources` — resource-scoped working memory (one row per `resourceId`/principal)
- `mastra.mastra_workflow_snapshot` — workflow run/suspend state (used by the `scheduled-report` workflow)

These tables are **not under drizzle-kit migration control** — they aren't declared under `src/infrastructure/database/schema/*` and have no drizzle migration; Mastra owns their DDL and lifecycle itself.

Our own `public.agent_conversation` table (drizzle-managed — see `repositories/conversation.repository.ts`) is a thin metadata layer _over_ a Mastra thread, not a duplicate of it: `agent_conversation.id` is generated by us but is then passed verbatim as the Mastra `thread.id` (see `agent-runner.service.ts`: `memory: { resource: conv.resourceId, thread: { id: conv.id } }`). The two ID spaces are deliberately the same value by construction, so our audit tables (`agent_run`, `agent_approval`, `agent_action_log`) can reference a conversation without a separate id-mapping table back to Mastra's own thread/message history.
